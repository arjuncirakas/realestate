# Estate Platform — Agent Rules

Web platform for a real estate agency dealing primarily in land plots. Public visitors browse and enquire; subscribers save plots, book visits, and register group-purchase interest; owners view holdings and management activity; agents and admins manage listings, media, queues, and ownership records. Group purchase records expressions of interest only — the platform never takes, holds, or moves money.

## Authority

`docs/PROJECT_REQUIREMENTS.md` is the authoritative spec. Read the relevant sections before writing code. If a chat instruction conflicts with that document, the document wins — stop and report the conflict rather than silently diverging.

## Stack

- JavaScript ESM only. No TypeScript, no `.ts` files, no `@types/*` packages.
- Never `require()` — `import`/`export` only. Both `package.json` files declare `"type": "module"`.
- Backend dev server: `node --watch`, not nodemon.
- Tailwind v4 has **no** `tailwind.config.js`. Tokens live in `@theme` inside `frontend/src/index.css`.

## File ownership

Edit only your assigned paths (Section 13). The only shared files are:

- `backend/src/app.js` — one `import` line + one `app.use()` line per module
- `frontend/src/routes/index.jsx` — one `import` line + one route entry per feature

Anything larger goes to the lead.

## Contracts

- Only WP0 creates or edits `backend/src/contracts/`.
- `frontend/src/contracts/` is generated by `npm run contracts:sync` — never hand-edit it.
- Frontend forms import schemas from contracts; do not redefine validation locally.
- Every backend integration test must assert response shape:
  `expect(SomeResponseSchema.safeParse(res.body.data).success).toBe(true)`.
  This assertion is mandatory — there is no compiler on this project.

## Backend conventions

- Thin controllers: no Prisma calls, no business logic. Services own all data access.
- Every route validated via the `validate` middleware.
- Throw `AppError` subclasses; never hand-build an error response.
- Never leak stack traces or SQL to the client.
- Wrap async handlers in `asyncHandler`.
- Money is a **string**, not a number (convert Prisma `Decimal` with `.toString()`).
- Use the exact geo SQL patterns from Section 4.3 — do not invent your own.

## Frontend conventions

- One React Query hook per endpoint in `src/api/`; components never call axios directly.
- Structured array query keys: `['properties', 'list', filters]`.
- Every list has all four states: loading skeleton / empty / error / success. A bare spinner is unacceptable.
- Theme tokens only — no inline colour literals (`bg-[#…]`).
- No `localStorage` or `sessionStorage` for tokens.
- Buttons name their outcome ("Register interest"), never "Submit".

## Response envelope & error codes

Success: `{ "data": {}, "meta": {} }`  
Paginated: `{ "data": [], "meta": { "page", "limit", "total", "totalPages" } }`  
Error: `{ "error": { "code", "message", "details" } }`

| Code | Status |
|---|---|
| `VALIDATION_ERROR` | 400 |
| `UNAUTHENTICATED` | 401 |
| `FORBIDDEN` | 403 |
| `NOT_FOUND` | 404 |
| `CONFLICT` | 409 |
| `RATE_LIMITED` | 429 |
| `INTERNAL_ERROR` | 500 |

## Group purchase content (Section 1.3)

The group-purchase feature is an enquiry mechanism, not an investment product. All copy — page headings, button labels, form text, confirmation messages, emails — must use the language of *registering interest*. Prohibited anywhere in the codebase, including seed data and placeholder copy:

- Any stated, projected, guaranteed, or historical **return, yield, ROI, or appreciation figure**
- The words "invest", "investment", "investor", "shares", "units", "portfolio returns", "dividend"
- Countdown timers, funding progress bars expressed in money raised, or "X spots left" urgency devices
- Any implication that submitting the form creates a binding commitment or entitlement

Approved vocabulary: "register your interest", "indicative amount", "the agency will contact you", "group purchase opportunity", "enquiry". If unsure, use the plainer wording.

## Style

- JSDoc (`@param`, `@returns`) on every exported function.
- Named exports except React page components (default export).
- `kebab-case.js` modules, `PascalCase.jsx` components.
- Comments explain *why*, not *what*.
- No `console.log`. No `TODO` or commented-out code in finished work.

## Commands

```
npm run dev              # frontend + backend concurrently
npm run db:up            # docker compose up -d
npm run db:migrate       # prisma migrate dev
npm run db:seed          # seed data
npm run contracts:sync   # copy contracts to frontend
npm run contracts:check  # fail if contracts drift
npm run lint             # lint both packages
npm test                 # test both packages
```

## Definition of done

A work package is done when:

1. `npm run lint` passes with zero warnings in the affected package.
2. `npm test` passes.
3. `npm run contracts:check` passes.
4. New endpoints are documented in `docs/API.md` with request/response examples.
5. The feature works end to end against seeded data, verified manually.
6. No `TODO`, commented-out code, or `console.log` remains.
7. No files outside the package's owned paths were modified.

Run these yourself before reporting completion — do not leave the lead to discover a failure.
